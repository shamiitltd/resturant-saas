PART A - SYSTEM OVERVIEW
======================================================================

1. PRODUCT PURPOSE
------------------
The product is a shared, multi-tenant Restaurant Operating SaaS Platform.
It serves restaurants, cafes and restaurant chains.

The core customer flow is:
  SCAN TABLE QR
      -> OPEN RESTAURANT MENU
      -> SELECT AND CONFIGURE ITEMS
      -> SUBMIT ORDER
      -> KITCHEN AND RECEPTION RECEIVE THE ORDER
      -> CHEF ACCEPTS AND SETS ETA
      -> CUSTOMER TRACKS STATUS
      -> ORDER BECOMES READY
      -> WAITER SERVES OR CUSTOMER COLLECTS
      -> RECEPTION PREPARES/REVIEWS BILL
      -> CUSTOMER PAYS THE RESTAURANT DIRECTLY
      -> AUTHORIZED STAFF VERIFIES AND RECORDS PAYMENT

The platform also provides owner tools, staff permissions, a Super Admin
onboarding layer, optional games/rewards, a constrained content configurator,
and later-phase integrations/operations modules.

The platform's principal outcomes are:
- Reduce verbal order-taking errors.
- Provide customers with persisted order status and chef-confirmed ETA.
- Give kitchen, reception and waiters the same order record.
- Let owners publish offers without visiting tables.
- Onboard multiple restaurant businesses on one shared platform.
- Let owners safely edit supported customer-facing blocks without coding.
- Support optional games and rewards.
- Integrate with supported third-party tools instead of forcing replacement.
- Monetize through SaaS subscriptions and optional feature entitlements.

2. USERS AND RESPONSIBILITY BOUNDARIES
--------------------------------------

2.1 CUSTOMER / DINER
Responsibilities:
- Scan a table QR.
- View the correct restaurant/branch menu.
- Select menu items, variants/modifiers, quantities and optional notes.
- Submit an order.
- View persisted order status and chef ETA.
- Pay the restaurant directly using the restaurant's configured payment
  instructions or another payment method accepted by that restaurant.
- Optionally use eligible games and rewards.

Customer access rules:
- Basic dine-in ordering supports guest access; mandatory account creation is
  not required.
- Optional customer profile may support history/loyalty where implemented.
- Customer QR/table context is not a staff identity.
- A customer must not see another tenant's or another customer's private
  order/session information.

2.2 RECEPTION / CASHIER
Responsibilities:
- View incoming persisted orders and their table/session context.
- Review generated bills.
- Record restaurant-side payment details.
- Verify payment in the restaurant's own bank/UPI application or other
  external payment channel.
- Perform only authorized billing exceptions.

Reception does not re-enter every customer-selected item into a second order.
The bill is generated from persisted order/item snapshots and server-side
calculation rules.

2.3 CHEF / KITCHEN STAFF
Responsibilities:
- View KOTs for the correct branch/station.
- Accept or reject orders according to the configured policy.
- Update preparation status.
- Set or update the estimated preparation time (ETA).
- Mark the order READY when preparation is complete.

2.4 WAITER / SERVICE STAFF
Responsibilities:
- View READY orders eligible for their branch/section assignment.
- Pick up the prepared order.
- Record pickup and served status.

2.5 BRANCH MANAGER
Responsibilities:
- Supervise branch operations and permitted reports/actions.
- Perform only actions covered by assigned permissions and location scope.

2.6 OWNER
Responsibilities:
- Manage restaurant business profile and branches.
- Manage menus, items, prices, availability and modifiers.
- Manage tables and QR tokens.
- Publish, schedule and deactivate offers.
- Configure staff accounts, roles and permissions.
- Configure optional games/rewards and feature settings where entitled.
- Manage supported integrations.
- Edit allowed customer-facing content blocks.
- View basic operational reporting and later-phase analytics.

2.7 SUPER ADMIN (PLATFORM COMPANY)
Responsibilities:
- Create, activate, suspend and archive tenants.
- Invite restaurant owners.
- Assign plans and feature entitlements.
- Manage platform subdomains and verified custom domains as supported.
- Monitor usage and platform health.
- Perform authorized, audited support actions.

Super Admin is a platform-level authority and is not a restaurant staff role.
A restaurant owner cannot grant platform-admin authority.

3. TENANT, BRANCH AND TABLE HIERARCHY
-------------------------------------

The platform uses this hierarchy:

  PLATFORM
    |
    +-- TENANT A (Restaurant Business / Chain)
    |     |
    |     +-- LOCATION A1 (Branch)
    |     |     +-- TABLE 01
    |     |     |     +-- QR TOKEN
    |     |     |     +-- TABLE SESSION
    |     |     |           +-- ORDER 1 -> ORDER ITEMS -> KOT/STATUS EVENTS
    |     |     |           +-- ORDER 2 -> ORDER ITEMS -> KOT/STATUS EVENTS
    |     |     |
    |     |     +-- TABLE 02 ...
    |     |     +-- Branch Staff / Settings / Payment QR
    |     |
    |     +-- LOCATION A2 (Another Branch)
    |     +-- Tenant Menu / Offers / Users / Entitlements / Branding
    |
    +-- TENANT B (Another Restaurant Business)
          +-- Its own Locations / Tables / Orders / Staff / Settings

Definitions:
- TENANT = one restaurant business or restaurant chain using the SaaS.
- LOCATION = one physical restaurant branch/outlet belonging to a tenant.
- TABLE = a table belonging to one location.
- QR TOKEN = secure, revocable token resolving one table context.
- TABLE SESSION = dining visit context grouping one or more submitted orders.
- ORDER = an individual customer-submitted order and its KOT/status lifecycle.

Every tenant-owned row is tenant-scoped. Branch operational records are also
location-scoped where applicable. One restaurant's data must never be
accessible to another restaurant.

4. OVERALL SYSTEM ARCHITECTURE AND DATA FLOW
--------------------------------------------

4.1 Application experiences

  CUSTOMER QR / PWA
  STAFF DASHBOARD (Reception / Chef / Waiter / Manager)
  OWNER DASHBOARD
  PLATFORM SUPER ADMIN DASHBOARD
                  |
                  v
          NEXT.JS WEB APPLICATION
             (PROPOSED)
                  |
                  v
          BACKEND APPLICATION API
          (NESTJS OR FASTAPI - OPEN)
                  |
        +---------+----------+
        |         |          |
        v         v          v
   SUPABASE   SUPABASE   SUPABASE
   POSTGRES   AUTH/RLS   STORAGE / REALTIME
        |
        v
   TRANSACTIONAL OUTBOX
        |
        v
   BACKGROUND WORKER + REDIS QUEUE
        |
        +---- Notifications
        +---- Company gateway webhooks/reconciliation
        +---- Attendance/POS/inventory connectors
        +---- Scheduled offers/subscription jobs

4.2 Important architecture behavior
- PostgreSQL/Supabase is the source of truth for business state.
- Realtime messages notify clients; they are not the authoritative record.
- Critical writes must be transactional and idempotent.
- Backend must validate permissions, tenant and location scope.
- Games, CRM, integrations and inventory remain modular.
- Start with a modular monolith, not one microservice per module.
- A separate worker process may be deployed for background jobs.
- Supabase Realtime Broadcast/private channels are the initial realtime
  approach; a dedicated game gateway is conditional on future requirements.

5. CORE SYSTEM INVARIANTS
-------------------------

INVARIANT 01: Shared multi-tenant platform; no per-restaurant code fork.
INVARIANT 02: Tenant = business/chain; location = physical branch.
INVARIANT 03: Tenant-owned data always carries tenant scope.
INVARIANT 04: Branch operational data also carries location scope.
INVARIANT 05: Backend/database state is authoritative, not browser state.
INVARIANT 06: Order status and bill/payment status are independent.
INVARIANT 07: Restaurant diner payments and company SaaS payments are separate.
INVARIANT 08: Customer UPI QR/reference is not proof that payment was received.
INVARIANT 09: Only authorized staff can verify restaurant payment.
INVARIANT 10: Only verified company-gateway events may update SaaS payment state.
INVARIANT 11: Repeated order submission must not create duplicate orders/KOTs.
INVARIANT 12: Realtime interruption must not lose persisted work.
INVARIANT 13: Owner content editing is limited to allowlisted blocks.
INVARIANT 14: Feature use requires entitlement and tenant setting where applicable.
INVARIANT 15: Never trust client-supplied tenant, location, role, price, tax,
             reward score, payment status or subscription entitlement.
INVARIANT 16: Restaurant IP address is not required for onboarding.

6. SUPER ADMIN WORKFLOW: ONBOARD A NEW RESTAURANT
------------------------------------------------
ACTOR: Super Admin
GOAL: Add a restaurant business to the shared SaaS platform and make it ready
      for owner configuration and a test order.

PRECONDITIONS:
- Super Admin is authenticated and has platform tenant-management permission.
- Required business and owner details are available.

WORKFLOW:
1. Super Admin opens Platform Dashboard.
2. Super Admin selects Add Restaurant / Create Tenant.
3. Enters restaurant business name and business/contact information.
4. Enters owner identity/contact information needed for invitation.
5. Enters the initial branch/location details.
6. Platform validates required fields and checks for duplicate slug/hostname
   according to platform rules.
7. Platform creates the tenant record.
8. Platform creates the first location record and default configuration.
9. Platform assigns a unique tenant slug/platform subdomain.
10. Platform invites the restaurant owner through the configured invitation
    process.
11. Owner receives the invitation and completes account setup.
12. Owner enters/finishes branch settings, branding, menu, service mode,
    applicable tax configuration and table setup.
13. Platform/owner creates tables and generates a unique QR token for each
    active table.
14. Owner configures staff and location-scoped roles/permissions.
15. Owner and/or Super Admin performs a test order and notification test.
16. Super Admin activates the tenant after required setup/test completion.
17. The restaurant starts operating through its tenant URL.
18. If a custom domain is needed, it is handled as an optional verified
    domain mapping; it is not required for initial onboarding.

EXPECTED RESULT:
- One tenant exists with one or more locations.
- Owner can access the owner dashboard.
- The tenant has a unique platform slug/subdomain.
- Branch/menu/table configuration can be completed without custom deployment.
- Tenant is active only after authorized activation.

ERROR / EXCEPTION PATHS:
- Duplicate slug: reject and request a different slug.
- Invalid owner invitation target: report failure; do not create fake identity.
- Missing mandatory business/branch data: keep onboarding incomplete.
- Failed test order or notification: do not treat test as passed; record issue.
- Cross-tenant access attempt: deny and log security event where applicable.

IMPORTANT:
- Do not collect restaurant IP address for normal onboarding.
- Do not create one app deployment or database project per restaurant.
- Do not invent legal/business fields not defined by approved launch policy.

TRD TRACE: Sections 1, 3, 4, 5, 17 and 18.

--------------------------------------------------
ACTOR: Restaurant Owner
GOAL: Configure the first branch so it can receive real dine-in orders.

PRECONDITIONS:
- Tenant has been created by Super Admin.
- Owner invitation has been accepted and owner membership is active.

WORKFLOW:
1. Owner signs in.
2. Backend validates authentication, tenant membership and owner permissions.
3. Owner selects the tenant/branch context they are authorized to manage.
4. Owner completes restaurant/branch profile and contact information.
5. Owner configures branch timezone and operational settings.
6. Owner selects the branch service mode:
   a. TABLE SERVICE, or
   b. SELF SERVICE.
7. Owner configures the menu categories and menu items.
8. Owner configures item descriptions, images, prices, variants/modifiers,

9. Owner publishes the menu.
10. Owner creates branch tables.
11. Platform generates unique QR tokens for active tables.
12. Owner downloads/prints/displays the QR codes at the matching tables.
13. Owner configures the branch's restaurant-owned UPI QR/payment instructions
    or other accepted restaurant payment method.
14. Owner adds staff and assigns roles/location scope.
15. Owner optionally configures offers and other features available to the
    tenant under its current entitlement.
16. Owner verifies the customer menu and performs a test order.

EXPECTED RESULT:
- Branch is configured with menu, tables, QR codes, service mode and payment

- Correct staff can access the branch dashboards.
- A test order can be processed end-to-end.

8. IDENTITY, STAFF ACCESS AND PERMISSIONS WORKFLOW
-------------------------------------------------
ACTORS: Owner, Manager, Staff Member, Super Admin (platform scope only).

8.1 Staff onboarding
1. Owner/authorized manager opens Staff Management.
2. Creates/invites a staff member.
3. Assigns tenant membership.
4. Assigns one or more permitted location/branch memberships.
5. Assigns a default role (Reception, Chef, Waiter, Manager) or an approved
   custom role if custom roles are enabled.
6. Backend stores membership/role/permission mapping.
7. Staff member accepts invitation/signs in.
8. Backend evaluates permission keys and location scope on each protected API.

8.2 Staff request authorization
Every protected action is evaluated using:
- Actor identity and account state.
- Active tenant membership.
- Required permission key.
- Resource tenant_id.
- Allowed location scope when branch-specific.
- Resource state and valid action transition.
- Feature entitlement where relevant.

Examples of permission keys from the TRD:
- orders.view / orders.create / orders.cancel / orders.update_status
- kitchen.view / kitchen.accept / kitchen.update_eta / kitchen.mark_ready
- billing.view / billing.create / billing.verify_payment / billing.refund
- menu.view / menu.create / menu.update / menu.publish
- offers.view / offers.manage / offers.publish
- staff.view / staff.create / staff.manage_roles
- inventory.view / inventory.update
- subscriptions.view / subscriptions.manage
- platform.tenants.create / platform.tenants.suspend / platform.plans.manage

8.3 Staff deactivation or role change
1. Owner/authorized manager changes role, location assignment or active state.
2. Backend checks permission to make the change.
3. Change is persisted and audited.
4. Subsequent protected requests use the updated membership/permission state.
5. A deactivated/unassigned staff user is denied unauthorized requests.

RULES:
- UI hiding is not authorization; API must enforce permission.
- A tenant owner cannot grant platform-admin scope.
- Branch staff cannot access unassigned branches unless another explicit
  authorized assignment exists.

9. OWNER WORKFLOW: MENU, TABLES AND QR MANAGEMENT
------------------------------------------------
ACTOR: Owner or permitted manager.

9.1 Menu lifecycle
1. Owner opens Menu Management.
2. Creates/updates categories.
3. Creates/updates menu items.
4. Sets name, description, image, category and price.
5. Configures variants and modifier groups/options.
6. Configures branch availability.
7. Saves draft/configuration.
8. Publishes menu changes.
9. Customer menu reads the published/active menu for the resolved tenant and

10. Backend remains authoritative for current price and availability at order

1. Owner opens Table Management for a branch.
2. Creates a table record.
3. Platform generates a cryptographically random QR token.
4. Platform stores token hash where feasible and provides QR output for display.
5. QR token resolves only to the intended tenant/location/table.
6. If QR must be replaced, owner rotates/revokes the old token.
7. Revoked/unknown/inactive token is rejected by the resolver.

10.1 Offer lifecycle

2. Creates an offer.

11. CUSTOMER WORKFLOW: QR RESOLUTION AND MENU DISCOVERY
-------------------------------------------------------
ACTOR: Customer (guest or optional authenticated customer).

PRECONDITIONS:
- Restaurant tenant is active.
- Branch is configured and table is active.
- QR token has not been revoked.
- Published menu is available.

WORKFLOW:
1. Customer scans the QR displayed at a restaurant table.
2. Browser opens the tenant-aware customer route.
3. Platform resolves the trusted hostname/tenant slug.
4. Backend receives the QR token and resolves it server-side.
5. Backend validates token, tenant, location and table status.
6. Backend creates or resolves the applicable active table-session context
   according to the table-session policy.
7. Customer sees the correct restaurant/branch menu.
8. Customer browses published categories/items and current availability.
9. Customer selects an item and configures supported variant/modifier choices.
10. Customer changes quantity and optional supported kitchen note.
11. Customer adds, edits or removes cart lines before submission.

ERROR PATHS:
- Invalid/revoked QR: reject table resolution and do not open an order context.
- Inactive tenant/branch/table: do not permit ordering.
- Unavailable item: do not accept that item in a new order.
- Reconnecting browser: load persisted state through API; do not assume browser
  memory is the source of truth.

PRD TRACE: FR-ORD-01 through FR-ORD-04; FR-IAM-01.
TRD TRACE: Sections 4, 5, 13 and 15.

12. CUSTOMER WORKFLOW: CART AND ORDER SUBMISSION
------------------------------------------------
ACTOR: Customer.

WORKFLOW:
1. Customer reviews the cart.
2. Customer confirms the order.
3. Frontend sends selected item identifiers, quantities, modifiers, optional
   notes, table/session context and an idempotency key.
4. Backend ignores/rejects client-supplied prices, totals, tax amounts,
   tenant identity, role and payment status as authoritative values.
5. Backend derives tenant/location/table context from validated QR/session
   and server-side authorization context.
6. Backend validates that the table session is eligible to accept orders.
7. Backend checks the idempotency record/key.
8. Backend loads authoritative menu item/variant/modifier prices.
9. Backend checks branch-specific item availability.
10. Backend evaluates eligible offers and quotas.
11. Backend calculates subtotal, tax, discount and total in integer minor
    currency units using the approved server configuration.
12. Backend creates the order header.
13. Backend stores immutable order-item snapshots including item names,
    selected modifiers, quantity and price at submission time.
14. Backend creates the initial order status event.
15. Backend creates the transactional outbox event for ORDER_PLACED.
16. Backend stores the idempotency result/reference.
17. Database transaction commits.
18. Backend returns the persisted order reference/status to the customer.
19. Customer order view loads persisted state and subscribes to authorized
    order updates where realtime is available.

TRANSACTION RULE:
If the transaction fails, no committed order or corresponding outbox event
may remain. If the same submission is retried with the same idempotency key,
it must return the same order rather than create another order/KOT.

PRD TRACE: FR-ORD-03 through FR-ORD-08; BR-06, BR-07, BR-14.
TRD TRACE: Sections 6, 7, 8 and 9.

13. BACKEND WORKFLOW: ORDER PERSISTENCE AND NOTIFICATION FAN-OUT
-----------------------------------------------------------------
ACTORS: Backend API, PostgreSQL, outbox worker, Realtime, kitchen and reception.

WORKFLOW:
1. Order creation transaction completes and commits.
2. The outbox worker finds the pending ORDER_PLACED record.
3. Worker publishes an authorized event to the correct tenant/location
   staff channel and relevant kitchen/reception audience.
4. Kitchen dashboard receives a notification and loads the persisted KOT/order.
5. Reception dashboard receives a notification and loads persisted order and
   table/session details.
6. Each dashboard confirms/refreshes from the API/database rather than
   treating the event payload as the complete source of truth.
7. Worker marks successful delivery according to the delivery strategy.
8. Transient publish failures are retried with bounded exponential backoff
   and jitter.
9. After the configured retry limit, event is dead-lettered/alerted for review.

IMPORTANT:
- Notification delivery failure must not roll back a valid order.
- A repeated event must not create duplicate KOTs/tasks.
- Broad channels must not expose private customer or payment details.
- All channels must enforce tenant/location/resource authorization.

TRD TRACE: Sections 7, 9, 15 and 16.

14. CHEF WORKFLOW: KITCHEN ORDER PROCESSING AND ETA
--------------------------------------------------
ACTOR: Chef/Kitchen Staff.

PRECONDITIONS:
- Chef is authenticated.
- Chef has an active membership and kitchen permissions for the branch.
- KOT belongs to the chef's permitted tenant/location/station.

WORKFLOW:
1. Chef opens Kitchen Dashboard/Kitchen Queue.
2. Dashboard loads current persisted eligible KOTs for the branch/station.
3. New order notification may arrive through Realtime.
4. Chef opens the KOT and reviews item names, quantities, modifiers, notes
   and order age.
5. Chef accepts or rejects the order according to configured policy.
6. Backend validates the allowed state transition and permission.
7. Backend persists the new status and order_status_event with actor/time.
8. If accepted, chef sets the estimated preparation time (ETA).
9. Backend persists ETA and its update history.
10. Realtime event informs the authorized customer, reception and staff views.
11. Chef updates order to PREPARING when preparation begins.
12. Backend validates and persists the transition.
13. When preparation is complete, chef marks the order READY.
14. Backend validates and persists READY state and event.
15. The READY event is routed according to the branch service mode.

EXCEPTION PATHS:
- Invalid transition: backend rejects it.
- Unauthorized branch/station access: deny and audit where appropriate.
- Realtime failure: state remains persisted; dashboards recover using API.
- Reject/cancel: use allowed exception path and record actor/reason where policy
  requires it; do not directly rewrite status.

ORDER STATUS PATH:
PLACED -> ACCEPTED -> PREPARING -> READY -> SERVED -> COMPLETED

Allowed exceptions defined by TRD:
- PLACED -> REJECTED or CANCELLED
- ACCEPTED -> CANCELLED (policy/permission required)
- PREPARING -> CANCELLED (manager override/reason may be required)
- READY -> CANCELLED only as an audited exception

REJECTED, CANCELLED and COMPLETED are terminal for normal workflow.

PRD TRACE: FR-OPS-01, FR-OPS-02, FR-OPS-03, FR-ORD-08.
TRD TRACE: Sections 7, 8, 9 and 15.

15. RECEPTION WORKFLOW: ORDER VISIBILITY AND BILL PREPARATION
-------------------------------------------------------------
ACTOR: Reception/Cashier.

WORKFLOW:
1. Reception dashboard loads persisted orders for its authorized branch.
2. An ORDER_PLACED notification may alert reception to a new order.
3. Reception opens the order/table-session record.
4. Reception reviews order items, quantities, modifiers, snapshots and totals.
5. Reception does not manually re-enter the customer's line items.
6. Reception generates/reviews a restaurant bill from persisted order snapshots
   and approved server-side calculation rules.
7. Bill is linked to eligible order(s) and the applicable table/session context.
8. Reception sees the restaurant's configured payment instructions/QR for the
   correct branch when payment is requested.
9. Reception can track order progress independently from payment status.

BILLING RULES:
- Bill total derives from persisted order snapshots and server calculation.
- Historical item name/price/modifier snapshots remain available even if the
  live menu item changes later.
- Order READY does not imply bill PAID.
- Exact bill timing/settlement policy follows the restaurant's approved
  operational policy; do not invent a mandatory pay-before-serving rule.

PRD TRACE: FR-OPS-04, FR-BILL-01, FR-BILL-03.
TRD TRACE: Sections 6, 7 and 10.

16. READY HANDOFF: WAITER SERVICE OR SELF-SERVICE
------------------------------------------------
ACTOR: Backend routing, Waiter, Customer.

DECISION:
The branch's configured service mode determines the READY handoff.

PATH A - TABLE SERVICE
1. Chef marks order READY.
2. Backend persists READY and creates/publishes the ORDER_READY event.
3. Waiter/service dashboard receives a task for an eligible order within its
   authorized branch/section scope.
4. Waiter opens the ready order and verifies destination/table details.
5. Waiter collects the prepared order.
6. Waiter records pickup through the authorized action.
7. Backend persists pickup status/event.
8. Waiter delivers the order to the correct table.
9. Waiter marks the order SERVED.
10. Backend persists SERVED status/event.
11. The order may proceed to COMPLETED under the defined workflow/policy.

PATH B - SELF SERVICE
1. Chef marks order READY.
2. Backend persists READY and creates/publishes ORDER_READY event.
3. Customer order interface receives the authorized ready/pickup notification.
4. Customer is instructed that the order is ready for collection.
5. Order remains persisted; reconnect/refresh recovers current state.
6. Completion handling follows the approved service/order policy.

Do not route a self-service READY order into the waiter pickup queue.
Do not route a table-service READY order only to customer pickup notification.

18. TABLE-SESSION LIFECYCLE
---------------------------
STATUS: PROPOSED V1 MODEL; PRODUCT CONFIRMATION REMAINS OPEN.

The PRD/TRD proposed V1 table-session behavior is:
- One active OPEN table session per table at a time unless future policy allows
  concurrent sessions.
- One table session can group multiple separately submitted customer orders.
- Each customer's confirmed submission remains a separate order and KOT.
- Each order is linked to the same table session.
- Draft carts remain private to the customer's browser/session by default.
- Reception may generate one consolidated bill from eligible orders in the
  table session.
- Split billing is not included in V1 unless approved.
- Table session closes only when there are no active orders and bill/payment
  policy is satisfied.
- Reopening requires permission and audit.

FLOW:
1. First valid customer QR context enters or creates the active table session.
2. Customer keeps their own draft cart private.
3. Customer submits an order; a separate order/KOT is created.
4. Another customer at the same table may submit another separate order.
5. Both orders link to the same active table session if V1 table-session policy
   is approved.
6. Reception reviews eligible session orders.
7. Reception can consolidate eligible orders into a bill under the proposed
   V1 model.
8. Split billing is excluded unless separately approved.
9. Once no active orders remain and payment/bill conditions are satisfied,
   the table session can close.
10. Reopening a closed session requires authorized action and audit.

Do not implement this proposed model as a final product decision until
OPEN-PRD-02 / OPEN-TRD-05 is approved.

TRD TRACE: Section 6.3, ADR-09, OPEN-TRD-05.

19. GAMES AND REWARDS WORKFLOW
------------------------------
PHASE: Single-player engagement is Phase 1.5 SHOULD; multiplayer is Phase 2
COULD / requires its own scope and transport decision.

PRECONDITIONS:
- Tenant has the applicable plan entitlement.
- Owner has enabled the game feature for the tenant.
- Game is available for the applicable restaurant/location context.

19.1 Single-player game flow
1. Customer opens the game area while using the restaurant customer interface.
2. Backend checks tenant entitlement and owner feature toggle.
3. Backend returns eligible games.
4. Customer starts a game session.
5. Backend creates a session linked to tenant/location and optionally table
   session, with guest or authenticated customer identity context.
6. Customer plays the game.
7. Client submits completion/result data.
8. Backend validates session state, timing, answers/score and attempt limits.
9. Backend records verified game result and the rule version used.
10. If a reward rule is satisfied, backend validates reward eligibility,

13. On redemption, backend revalidates expiry, limits and eligibility.

5. Server validates game state, timing, answers and score.
6. Result is stored with its applicable rule version.
7. Reward, if eligible, follows the same server-side validation and ledger.

REWARD SAFETY:
- Client-provided score is never trusted as final.
- Duplicate result cannot issue duplicate reward.
- Concurrent redemption cannot exceed quota.
- Cooldowns and attempt limits prevent abuse.
- Game feature entitlement AND owner enablement are both required.

27. REALTIME EVENT DELIVERY AND RECOVERY
----------------------------------------

27.1 Source-of-truth rule
- Business state is first persisted in PostgreSQL.
- Outbox event is committed in the same transaction as the state change.
- A worker publishes events through authorized Supabase Realtime channels.
- Realtime is a notification/delivery mechanism, not the authoritative store.

27.2 Event publishing workflow
1. Business transaction updates order/bill/offer/game state.
2. Same transaction inserts a notification_outbox record.
3. Transaction commits.
4. Worker claims a pending outbox record.
5. Worker publishes event with stable event ID, tenant/location/resource IDs,
   type, timestamp, schema version and minimum safe payload.
6. Worker marks delivery according to publish acknowledgement strategy.
7. On transient error, worker retries with bounded exponential backoff+jitter.
8. After max attempts, worker dead-letters/alerts the event.
9. Event consumers process idempotently by event ID.

27.3 Client reconnect workflow
1. Client detects disconnect/reconnect.
2. Client re-authenticates/resolves its current permitted context as needed.
3. Client fetches current persisted state from REST/API.
4. Client refreshes order queue/status using last known cursor/version where
   supported.
5. Client resumes authorized Realtime subscriptions.
6. Missed notifications do not cause missed business state because database
   records remain authoritative.

27.4 Channel authorization
- Staff channel: only authenticated staff with matching tenant/location scope.
- Kitchen channel: kitchen staff and authorized manager for that location.
- Waiter channel: staff authorized for branch/section.
- Customer order channel: only the relevant customer/session can observe it.
- Game room channel: only authorized room participants.
- Never trust a client-supplied tenant ID or arbitrary channel name.

TRD TRACE: Section 9.

28. ORDER, RESTAURANT PAYMENT AND SUBSCRIPTION STATE MACHINES
------------------------------------------------------------

28.1 ORDER STATE
PLACED -> ACCEPTED -> PREPARING -> READY -> SERVED -> COMPLETED

Allowed exceptions:
PLACED -> REJECTED or CANCELLED
ACCEPTED -> CANCELLED (policy/permission required)
PREPARING -> CANCELLED (manager override/reason may be required)
READY -> CANCELLED only as an audited exception

REJECTED, CANCELLED and COMPLETED are terminal for normal workflow.
Every transition must store actor, role, timestamp, old/new state and optional
reason. Backend validates the transition and resource scope.

UNPAID -> PARTIALLY_PAID (only if partial payment is approved)
UNPAID/PAYMENT_REPORTED -> VOIDED (authorized reason)
VERIFIED_PAID -> REFUNDED/ADJUSTED via approved correction workflow only.

Payment status is independent of order status.

28.3 SAAS SUBSCRIPTION STATE
PENDING -> ACTIVE -> PAST_DUE -> GRACE_PERIOD -> ACTIVE or EXPIRED
ACTIVE -> CANCELLED (paid-through access depends on policy)
ACTIVE -> RENEWAL_PENDING -> ACTIVE (verified successful gateway event)

32. FAILURE AND RECOVERY WORKFLOWS
----------------------------------

32.1 Order submission retry
- Client sends an idempotency key.
- If network response is lost, client retries with the same key.
- Backend returns the existing order result rather than creating a duplicate.
- A new key is used only for a genuinely new submission.

32.2 Realtime interruption
- Order/state remains in PostgreSQL.
- Outbox publication retries.
- Client reconnects and fetches persisted current status/queue.
- Notification delivery failure does not roll back a committed order.

32.3 Worker/queue failure
- Durable job remains queued/pending.
- Worker restart resumes eligible jobs.
- Transient failures retry with bounded backoff.
- Max-attempt failures are dead-lettered/alerted for review.

32.4 Customer payment uncertainty
- Customer-entered reference stays unverified.
- Staff checks restaurant bank/UPI account externally.
- Only authorized staff marks payment verified.
- Verification actor/time/amount/reference are retained and audited.

32.5 SaaS gateway webhook uncertainty
- Backend validates signature and event identity.
- Duplicate webhook is idempotently ignored/reconciled.
- Invalid signature or event does not activate entitlement.
- Successful verified event updates subscription according to approved policy.

32.6 Integration failure
- Sync run records error and provider context safely.
- Transient provider/network error is retried.
- Permanent mapping/validation error is visible for correction.
- Reprocessing must not duplicate normalized records.

32.7 Tenant/branch authorization failure
- Request is denied.
- No cross-tenant or unassigned-branch data is returned.
- Security-relevant event is logged according to audit policy.

32.8 Domain verification failure
- Unverified/duplicate hostname is not activated.
- Tenant keeps its platform slug/subdomain route.

32.9 File/asset failure
- Customer/owner UI shows safe failure state.
- Existing valid asset/configuration remains authoritative until a valid update
  has been stored and published.

SCENARIO 04: MULTIPLE CUSTOMERS AT ONE TABLE (PROPOSED V1)
1. Multiple customers scan the same table QR.
2. Each browser/customer context keeps its own draft cart private.
3. Each customer submission creates a separate order/KOT.
4. Under the proposed table-session model, orders link to one active session.
5. Reception can consolidate eligible orders into one bill.
6. Split bill is not included unless approved.
EXPECTED: behavior only becomes binding after table-session decision approval.

SCENARIO 05: RESTAURANT CUSTOMER PAYS BY RESTAURANT UPI QR
1. Bill exists.
2. Customer views restaurant's branch-specific QR/instructions.
3. Customer pays the restaurant through their UPI/banking application.
4. Customer may provide a reference claim if enabled.
5. Reception verifies actual receipt in restaurant bank/UPI application.
6. Authorized staff records verified payment.
EXPECTED: SaaS company gateway is never involved in diner food payment.

SCENARIO 06: OWNER PUBLISHES AN OFFER
1. Owner opens Offers.
2. Creates offer details and approved conditions.
3. Defines validity, branch scope and usage limits.
4. Publishes/schedules offer.
5. Backend makes offer available according to lifecycle.
6. Customer interface shows active eligible offer.
7. Order submission revalidates offer at server side.
8. Quota/redemption record is saved transactionally.
EXPECTED: no manual table-by-table announcement and no client-trusted discount.

SCENARIO 07: GAME REWARD IS ISSUED
1. Customer opens games.
2. Backend verifies tenant feature entitlement and owner enablement.
3. Customer starts a session.
4. Backend records session and validates completion/result.
5. Backend evaluates reward rule and limits.
6. Backend issues reward transactionally if eligible.
7. Customer sees reward.
8. Redemption revalidates expiry, branch applicability, quotas and limits.
EXPECTED: forged/duplicate score cannot create duplicate reward.

SCENARIO 08: RESTAURANT BUYS/RENEWS A SAAS PLAN
1. Owner opens SaaS subscription page.
2. Owner selects available plan/billing cycle.
3. Backend creates pending checkout/invoice/payment attempt.
4. Backend starts checkout with company's selected gateway.
5. Owner pays SaaS company using provider checkout.
6. Gateway sends webhook to backend.
7. Backend verifies signature/event identity and processes idempotently.
8. Verified success updates SaaS subscription and entitlement.
9. Feature access follows server-side entitlement/grace policy.
EXPECTED: company gateway is used only for SaaS subscription payment.

SCENARIO 09: ATTENDANCE DATA SYNCHRONIZES
1. Owner configures an actually supported connector or chooses file import.
2. Connection is tested or file is validated.
3. External employee identifiers are mapped to platform staff identifiers.
4. Provider data is normalized.
5. Sync run and record provenance are saved.
6. Duplicate source records are prevented.
7. Errors/retries are shown to authorized owner/manager.
EXPECTED: supported data is imported reliably; unsupported providers are not
represented as already integrated.

SCENARIO 10: REALTIME SERVICE IS INTERRUPTED
1. An order/status update commits to PostgreSQL.
2. Outbox record is saved in the same transaction.
3. Realtime publish fails or client disconnects.
4. Worker retries publication.
5. Client reconnects and fetches authoritative current state through API.
6. Client resumes authorized subscriptions.
EXPECTED: committed order/state is not lost due to realtime outage.

PART E — EXTERNAL FOOD-DELIVERY MARKETPLACE ORDER WORKFLOW (ADDED IN v1.2)
===============================================================================

SCOPE AND STATUS
---------------
This section describes the intended workflow for orders placed by customers
on supported third-party food-delivery marketplaces such as Zomato and Swiggy.
It is conditional on an approved direct POS/partner integration or an
authorized aggregation provider. It does not assert that any provider access,
commercial eligibility, credentials, certification or sandbox is already
available. PRD and TRD v1.0 remain authoritative.

ACTORS
------
- Marketplace customer: places an order in the marketplace app.
- Marketplace / authorized aggregator: delivers order events and receives
  acknowledgements/status updates under its contract.
- Restaurant reception / manager: monitors and accepts/rejects orders where
  the provider workflow permits.
- Kitchen staff: prepares accepted orders.
- Restaurant owner/admin: connects and maps the provider outlet to a branch.
- Platform integration worker: validates, normalizes, dispatches and retries
  provider events/actions.

PRECONDITIONS
-------------
- A provider connector route has been approved by the product owner.
- Current provider/aggregator API documentation and contractual permissions
  are available.
- Credentials, webhook verification details and sandbox/test outlet access
  have been issued through the provider's approved process.
- The marketplace outlet is mapped to the correct SaaS tenant and branch.
- Required menu/item mapping and operational settings are configured where
  the connector requires them.

ORDER INGESTION WORKFLOW
------------------------
1. A customer places an order in a supported marketplace.
2. The marketplace or authorized aggregator emits an order event/webhook.
3. The platform receives the event at the provider-specific integration edge.
4. The platform authenticates/verifies the event according to the provider
   contract; invalid events are rejected and safely logged.
5. A durable inbox record is written before asynchronous processing. The
   provider event ID / external order ID is used for deduplication.
6. The provider adapter maps the source payload into the canonical external
   order model without leaking provider-specific fields into core order logic.
7. The connector resolves provider outlet ID to tenant_id and location_id.
   Unknown or ambiguous mappings go to an error/review queue; never guess.
8. The order and item/modifier snapshots, source references, initial internal
   state and outbox event are committed transactionally.
9. The order appears in the branch's External Orders queue with source label,
   external reference, order timer/acknowledgement deadline where supplied,
   items, quantities, modifiers, instructions, amounts and permitted
   fulfilment/customer details.
10. Reception/manager receives a prominent visual and audible alert where
    supported by the UI/device settings.

STAFF ACCEPT / REJECT WORKFLOW
------------------------------
11. An authorized staff member reviews the order and its acknowledgement
    deadline.
12. Staff accepts or rejects the order in the unified platform dashboard.
13. The backend validates actor permissions, current order state, provider
    deadline/rules and any provider-specific reason requirements.
14. The action is committed with actor/time and an idempotency key.
15. An outbox job dispatches the mapped accept/reject action to the provider.
16. Provider acknowledgement is stored and displayed. A timeout, rejection,
    rate limit or connection failure remains visible and is retried/reconciled
    according to provider policy; do not show a false success.
17. If provider acknowledgement deadline expires, the UI clearly indicates
    the state and the connector follows the provider's documented timeout
    behavior. Never invent or override marketplace rules.

KITCHEN AND STATUS WORKFLOW
---------------------------
18. Once accepted according to the provider workflow, the canonical order is
    routed to the correct branch kitchen queue as an external-channel KOT.
19. Kitchen staff see a clear marketplace/source label and external order
    reference; no dine-in table is required.
20. Chef/kitchen staff update preparation status using permitted transitions.
21. The platform maps internal status to provider-supported status values.
22. Status updates are dispatched asynchronously and idempotently; provider
    acknowledgement, retry and failure state are retained.
23. Pickup/ready/handover events are sent only if supported by the provider
    contract. Delivery partner arrival/assignment events are displayed only
    when the provider supplies them.
24. Cancellation, refund, customer cancellation and delivery-partner events
    are reflected only to the extent exposed by the connector/provider.

FINANCIAL AND DATA BOUNDARIES
-----------------------------
- External marketplace orders are not dine-in table orders and do not require
  a table_session_id.
- Keep source_channel and fulfilment_type explicit (for example delivery or
  pickup) and preserve provider order identifiers.
- Do not include marketplace orders in dine-in consolidated table bills by
  default.
- Keep marketplace collection, COD, commission, discount, refund, charges
  and restaurant settlement distinct from restaurant UPI verification and
  from the SaaS company's subscription payment gateway.
- Store provider-supplied payment/settlement facts with provenance. Do not
  claim that funds have settled to the restaurant bank account without a
  verified settlement source and an approved reconciliation process.
- Store only customer/delivery personal data necessary to fulfil the order;
  follow the approved retention and privacy policy.

FAILURE AND RECOVERY PATHS
--------------------------
- Duplicate webhook: return/record idempotent handling; never create another
  canonical order or KOT.
- Invalid signature/authentication: reject; do not process the order.
- Unknown provider outlet mapping: quarantine for authorized review; do not
  route to a guessed tenant or branch.
- Provider API timeout/rate limit: bounded retry with backoff, visible status,
  dead-letter/alert after configured attempts and reconciliation support.
- Failed accept/reject acknowledgement: show pending/failed state accurately;
  do not tell staff that the marketplace accepted the action without proof.
- Status dispatch failure: preserve the internal order state, retry outbound
  synchronization and expose connector health/error details to authorized
  staff.
- Provider outage: preserve already ingested orders and local operational
  state; show integration degraded state. Follow the provider's documented
  fallback and avoid unapproved portal automation.

IMPLEMENTATION GATES FOR ANTIGRAVITY
------------------------------------
GATE 1 — PROVIDER READINESS
- Confirm direct POS/partner eligibility or authorized aggregator contract.
- Obtain current API/webhook documentation, sandbox, credentials, outlet
  mapping, certification and allowed-action details.
- Confirm commercial fees, support/SLA and pilot outlet.
- Approve privacy/retention and marketplace financial reconciliation policy.

GATE 2 — PROVIDER-NEUTRAL FOUNDATION
- Define canonical external order model and provider adapter interface.
- Define durable webhook inbox, provider event deduplication and outbox.
- Add tenant-safe outlet mapping and integration health/status records.
- Add provider-neutral tests and synthetic fixtures only.

GATE 3 — FIRST APPROVED CONNECTOR
- Implement only the selected provider's documented event/action contract.
- Add signature/authentication, contract fixtures, retry, reconciliation,
  idempotency, tenant-isolation and failure-path tests.
- Verify acceptance deadline, accept/reject, kitchen routing and status updates
  against provider sandbox/certification requirements.

GATE 4 — PILOT AND OPERATIONS
- Run an approved pilot outlet with staff training and support runbook.
- Monitor event lag, acknowledgement failures, duplicate events, stuck orders,
  provider API errors and reconciliation mismatches.
- Expand to another marketplace only after the first connector is stable.

OPEN DECISIONS — DO NOT GUESS
----------------------------

- First marketplace and pilot restaurant/outlet.
- Provider commercial eligibility, fees, support and certification.
- Exact supported order actions, event schema, acknowledgement deadlines and
  status mapping for each selected provider.
- Marketplace collection/COD, commissions, discounts, refunds, taxes,
  packaging/delivery charges and settlement reconciliation model.
- Personal data retention, masked customer details and staff access policy.
