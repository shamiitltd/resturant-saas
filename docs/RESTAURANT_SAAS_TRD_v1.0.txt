1. PURPOSE, STATUS AND ARCHITECTURE PRINCIPLES
----------------------------------------------

This TRD translates the product requirements into a logical implementation design. It is written so that the core contracts, domain model and security rules remain valid whether the company selects a TypeScript/NestJS backend or a Python/FastAPI backend.

[TABLE 4]
| Architecture status / Proposed baseline: Next.js + TypeScript frontend, Supabase PostgreSQL/Auth/Realtime/Storage, and a modular monolith backend. NestJS and FastAPI are both viable backend candidates. The framework and its ORM/queue pairing must be approved through the decision register before implementation is locked. |

1.1 Architecture principles
~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Multi-tenant by design: tenant and branch context are explicit in data, API authorization and audit records.
- Modular monolith first: domain modules are separated in code and dependency direction, but deployed as a small number of applications initially.
- PostgreSQL is the source of truth for orders, order status, bills, subscription state, rewards and configuration.
- Realtime is a delivery mechanism, not the source of truth. Clients can reconnect and fetch current state.
- Critical business operations are transactional and idempotent.
- Tenant-facing content configuration is schema-driven; user-supplied code is never executed.
- Third-party providers are isolated behind adapters and normalized internal contracts.
- Customer meal payment and company SaaS subscription payment are separate business domains, records and provider integrations.
- Security is enforced server-side and at the database boundary where applicable; frontend hiding is not authorization.

4. MULTI-TENANCY, DOMAINS AND IDENTITY
--------------------------------------

4.1 Tenant hierarchy
~~~~~~~~~~~~~~~~~~~~
[IMAGE OMITTED IN TEXT VERSION: Figure 2. Tenant and branch ownership model.]
Figure 2. Tenant and branch ownership model.
Tenant represents a restaurant business or chain. Location represents a branch/outlet. Shared tenant data includes memberships, roles, menu, offers, subscription and branding; branch data includes tables, orders, staff assignments, local payment settings and inventory.

4.2 Tenant resolution
~~~~~~~~~~~~~~~~~~~~~
- Platform subdomain pattern: {tenant-slug}.platform-domain.example. The hostname is resolved against an active tenant_domains record.
- Customer route pattern may include an explicit restaurant slug and table QR token. The server cross-checks both; it must not trust an arbitrary tenant_id supplied by the browser.
- Custom domains are optional. Owner/Super Admin initiates domain claim; platform verifies DNS ownership (TXT or CNAME challenge), validates host mapping and provisions SSL through the selected edge/hosting provider.
- No restaurant IP address is required for tenant onboarding or routing. IP allowlisting may be an optional enterprise security feature only if a real use case exists.
- Domain mapping changes are audited and cached mappings have invalidation rules.

4.3 Tenant context model
~~~~~~~~~~~~~~~~~~~~~~~~

[TABLE 10]
| TenantContext = { / tenant_id: UUID, / location_id: UUID | null, / actor_type: PLATFORM_ADMIN | TENANT_USER | CUSTOMER_GUEST, / actor_id: UUID | null, / membership_id: UUID | null, / role_ids: UUID[], / permission_keys: string[], / request_id: string, / auth_source: string / } |

TenantContext is derived by trusted backend middleware from a verified identity/session and resolved tenant/branch. A request body or URL parameter alone must never grant tenant scope.

4.4 Table QR design
~~~~~~~~~~~~~~~~~~~
- QR encodes a public URL with a high-entropy, non-sequential token or token reference; do not expose numeric database IDs.
- Store token hash or an equivalent protected representation where feasible; support revoke/rotate and audit.
- Resolve token to tenant, location and table on the server. Validate table is active and branch is accepting orders.
- QR is a table locator, not user authentication. Customer operations receive a short-lived guest/table session capability with restricted access.
- Rate-limit QR resolution and order submission. Provide operational mitigations for a copied QR (table session controls, staff confirmation or configurable order acceptance rules).

5. AUTHORIZATION AND SECURITY ARCHITECTURE
------------------------------------------

5.1 Identity and session
~~~~~~~~~~~~~~~~~~~~~~~~
- Supabase Auth is the proposed identity provider for owner/staff users. Customer guest sessions may be platform-issued, short-lived and limited to the active table/order context.
- Backend validates access token signature, issuer, audience, expiry and expected claims before using identity context.
- Membership, role and branch permissions are resolved server-side. Do not treat user-editable profile metadata as authorization truth.
- Require MFA for Super Admin and strongly recommend it for tenant owners. Support session revocation and staff offboarding.
- Use secure, HttpOnly, SameSite cookies or a well-reviewed token storage pattern for browser sessions; avoid long-lived sensitive tokens in localStorage.

5.2 RBAC model
~~~~~~~~~~~~~~

[TABLE 11]
| users / profiles / └── tenant_memberships (user_id, tenant_id, status) / ├── membership_roles (membership_id, role_id) / └── location_memberships (membership_id, location_id) / roles (tenant_id nullable for platform/default roles) / └── role_permissions (role_id, permission_id) / permissions (stable key, description, module) / Authorization decision = / authenticated actor / + active membership / + tenant match / + branch scope (when required) / + permission key / + resource-level rules |

5.3 Supabase RLS and backend access
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

[TABLE 13]
| Critical implementation rule / Never expose the Supabase service-role key in the browser. Service-role/privileged server credentials bypass normal RLS protections; if used by a backend, the backend must enforce authorization and tenant scope on every query. Prefer user-scoped access/RLS for client-visible data and least-privilege database roles for server data access. |

- Enable RLS on all tables exposed through Supabase APIs or reachable by non-owner roles.
- Policies must check active membership and matching tenant/location context; use helper functions only when they are security-reviewed and indexed appropriately.
- If backend uses a privileged database connection, centralize tenant scoping in repositories/query builders and add negative cross-tenant tests; RLS must not be assumed to protect a role that bypasses it.
- Limit browser-side direct database access to narrowly scoped public menu reads or approved realtime subscriptions. All critical writes go through backend application services.
- Realtime private channel authorization must check tenant/branch/order ownership. A customer must not subscribe to all tenant order events.

5.4 Security baseline
~~~~~~~~~~~~~~~~~~~~~

[TABLE 14]
| Control | Requirement |
| --- | --- |
| Transport | TLS for all external endpoints; HSTS where supported. |
| Secrets | Store provider keys and database credentials in a secret manager/environment vault; rotate and audit access. |
| Input validation | Validate and normalize all API payloads; apply size and content limits to notes, files and uploads. |
| Output safety | Escape user-generated content; sanitize rich text if ever supported; apply CSP and secure headers. |
| Rate limits | Apply per-IP, tenant, user and operation limits to QR resolution, order creation, login, games and webhooks. |

| Payment webhooks | Verify provider signature, timestamp/replay constraints, event identity and idempotency before processing. |
| Privacy | Collect minimum diner data; define consent, retention, access and deletion processes for applicable jurisdictions. |
| Dependency security | Automated dependency scanning, lockfiles, secret scanning and patch policy. |

6. CORE WORKFLOW AND STATE MACHINES
-----------------------------------

6.1 Order creation transaction
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
[IMAGE OMITTED IN TEXT VERSION: Figure 3. Order-to-service sequence (logical; realtime event delivery is asynchronous).]
Figure 3. Order-to-service sequence (logical; realtime event delivery is asynchronous).

[TABLE 15]
| BEGIN TRANSACTION / 1. Resolve and validate tenant + branch + table session. / 2. Validate idempotency key for actor/session. / 3. Load authoritative menu item and modifier prices. / 4. Verify item availability and offer eligibility. / 5. Calculate subtotal, taxes, discounts and total in minor units. / 6. Insert order header and immutable order-item price snapshots. / 7. Insert initial order_status_event. / 8. Insert notification_outbox event (ORDER_PLACED). / COMMIT / After commit: / - worker publishes authorized realtime notification; / - staff/customer clients fetch current order state; / - failed event delivery is retried without creating another order. |

Order creation must be atomic: no order header without its items, and no notification event that describes a transaction which later rolled back. Unique idempotency constraints prevent duplicate order creation from browser retries.

6.2 Order state machine
~~~~~~~~~~~~~~~~~~~~~~~

[TABLE 16]
| Current state | Allowed next states | Actor / rule |
| --- | --- | --- |
| PLACED | ACCEPTED, REJECTED, CANCELLED | Kitchen/authorized staff accept or reject; cancellation subject to policy. |
| ACCEPTED | PREPARING, CANCELLED | Kitchen begins preparation; cancellation requires permission/reason. |
| PREPARING | READY, CANCELLED | Kitchen marks ready; cancellation is controlled and audited. |
| READY | SERVED, CANCELLED (exception) | Waiter/service team marks served; exception requires manager permission. |
| SERVED | COMPLETED | Reception/system completes after bill/service policy is satisfied. |
| REJECTED / CANCELLED / COMPLETED | No normal transitions | Terminal states; reversal requires explicit corrective workflow and audit. |

6.3 Independent payment state machine
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

[TABLE 17]
| State | Meaning | Transition control |
| --- | --- | --- |
| UNPAID | Bill exists; no verified payment recorded. | Initial state. |
| PAYMENT_REPORTED | Customer or staff has entered a transaction reference; not verified. | Optional; never treated as paid automatically. |
| VERIFIED_PAID | Authorized staff confirms receipt using restaurant’s external UPI/bank channel. | Permission + audit + verifier timestamp. |
| PARTIALLY_PAID | Some amount has been verified but balance remains. | Future capability; requires payment allocation rules. |
| VOIDED / REFUNDED | Bill/payment reversed under authorized workflow. | Manager/finance policy; reason and external reference required. |

6.4 Table session model
~~~~~~~~~~~~~~~~~~~~~~~
Proposed behavior: a table session groups orders for one table visit. Each customer submission creates an independent order/KOT, linked to the current session. A table bill can aggregate eligible orders. To prevent cross-customer draft interference, draft carts are private to their browser session unless a future explicit shared-cart feature is enabled.
- Session status: OPEN, CLOSING, CLOSED.
- A session opens by configured rule (staff opens it or first valid order creates it).
- Only one current OPEN session per table should exist unless business policy explicitly permits overlap.
- A session closes only after active orders and bill/payment conditions meet configured rules.
- Reopening a closed session requires authorized staff and audit logging.

7.3 Database conventions
~~~~~~~~~~~~~~~~~~~~~~~~
- Use UUID primary keys; public URLs and QR tokens must not expose sequential database identifiers.
- Every tenant-owned table carries tenant_id. Every branch-scoped table also carries location_id where applicable.
- Use composite foreign keys or equivalent constraints where practical to ensure a child row cannot reference a parent from a different tenant.
- Money is stored as integer minor units (for example, paise) plus ISO currency code; do not use floating-point for monetary calculations.
- Store timestamps in UTC (timestamptz); display according to location timezone.
- Persist immutable price, tax, modifier and discount snapshots on order/bill records to preserve historical calculations.
- Use check constraints and explicit state transition services for valid statuses.
- Add indexes for tenant_id, location_id, created_at, status, table_id, order_number and frequently queried foreign keys.
- Define unique constraints for tenant slug, active domain hostname, table code within branch, idempotency keys within scope and external provider event IDs.
- Schema changes are managed through versioned SQL migrations; production data migrations are backward-compatible where possible.

8. API DESIGN AND ENDPOINT CATALOGUE
------------------------------------

8.1 API conventions
~~~~~~~~~~~~~~~~~~~
- Version prefix: /api/v1 or /v1; choose one convention and apply consistently.
- JSON request/response bodies; ISO-8601 UTC timestamps; money values in minor units with currency.
- Use consistent error format: code, message, request_id and optional field errors. Do not leak stack traces or secrets.
- Pagination: cursor-based for high-volume order/event lists; stable sorting by created_at and id.
- Require Idempotency-Key for order creation, subscription checkout creation and other retry-sensitive mutations.
- Use If-Match/version fields or equivalent optimistic concurrency for owner content updates where lost updates are possible.
- OpenAPI contract is the source for generated client types and API documentation.
- All authenticated endpoints derive tenant/branch scope from verified context, not from arbitrary client-supplied tenant_id.

9. REALTIME EVENTS AND DELIVERY RELIABILITY
-------------------------------------------

9.1 Initial approach
~~~~~~~~~~~~~~~~~~~~
Use Supabase Realtime Broadcast/private channels for initial order and operational updates. Use Presence only for lightweight participant/online state in game rooms. Do not use Realtime Postgres Changes as the only durable workflow mechanism. For higher-frequency game logic, evaluate a dedicated WebSocket service (for example Socket.IO) as a later component.

9.2 Outbox and retry model
~~~~~~~~~~~~~~~~~~~~~~~~~~
- Write notification_outbox in the same DB transaction as the business change.
- Worker claims pending events with a lease/lock strategy and publishes to Realtime or external notification providers.
- Store attempt count, next_attempt_at, last_error, published_at and event_id.
- Use exponential backoff with bounded retry and a dead-letter/manual-replay process.
- Consumers tolerate duplicate delivery by event_id and fetch authoritative state from the API.
- A reconnecting client requests current order/session state and can use a last-seen event cursor where event history is exposed.

11.4 External food-delivery order integrations
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The external food-order module shall be implemented as a provider-independent adapter boundary within the integration hub for marketplaces such as Zomato and Swiggy, subject to the relevant provider approval and connector route. The platform must not couple core order processing to one marketplace's payload, status names or authentication model. Direct marketplace integrations may be used only after the company has secured the required POS/technology-partner approval, credentials, outlet mapping and certification. An authorized aggregation middleware may be used where it provides a contracted and technically supported route to multiple marketplaces.

Logical inbound flow:
Marketplace / authorized aggregator -> signed webhook or provider event -> webhook inbox (durable raw event reference) -> signature/authentication validation -> provider/event deduplication -> provider adapter normalization -> canonical external order -> tenant/location/outlet mapping -> transactional order + items + status event + outbox -> staff External Orders queue and kitchen KOT.

Logical outbound flow:
Staff accept/reject/status action -> internal state transition + outbox -> provider-specific status mapper -> provider API/aggregator -> acknowledgement persisted -> retry/reconciliation if delivery fails.

Canonical external order fields should include: tenant_id, location_id, source_channel, provider_outlet_id, external_order_id, external_order_code, fulfilment_type (DELIVERY/PICKUP/OTHER), source_created_at, acknowledgement_deadline, currency, item and modifier snapshots, item-level/order-level discounts and charges, tax/packaging/delivery charge details where supplied, provider payment/collection indicator, permitted masked customer/delivery details, special instructions, source status, internal status and raw_payload_reference. Store only the personal data required to fulfil the order and apply the approved retention policy.

Technical requirements:
- Use a unique constraint on (provider, provider_account/outlet scope, external_order_id) and on (provider, provider_event_id) where the provider supplies event IDs. If no event ID exists, use a documented deterministic deduplication key based on provider order identity and event semantics.
- Persist inbound events before processing. Acknowledge webhooks only after durable acceptance according to the provider contract; process asynchronously through workers.
- Validate webhook signatures, tokens, timestamps and replay windows exactly as specified by each provider. Secrets and API credentials are stored in a managed secret store; database rows hold references only.
- Resolve provider outlet IDs to a tenant and location through an explicit, verified mapping. Never infer tenant ownership from untrusted payload fields alone.
- Normalize provider item/modifier IDs to internal menu entities where possible, but preserve source labels and source price snapshots. An unmapped item must be visible and must not be silently substituted.
- External orders use the shared canonical order domain but must not require a dine-in table or table session. Add explicit source_channel and fulfilment_type fields; retain provider order IDs and external status events.
- Provider-specific acknowledgement deadlines must be stored and displayed as countdowns. Do not auto-accept or auto-reject unless the provider supports it and the restaurant explicitly configures the policy.
- Model internal order state and external provider state separately. A mapping table/configuration converts provider statuses to canonical states; unsupported transitions are rejected and logged.
- Accept/reject and status updates must be idempotent. Store request/response metadata, provider correlation IDs, attempt count, next_retry_at and terminal failure/dead-letter status. Do not retry non-idempotent provider actions without a safe provider idempotency mechanism or reconciliation query.
- A provider timeout must not be interpreted as success. Query/reconcile order status where supported before repeating an ambiguous accept/reject action.
- Route accepted external orders to the correct kitchen station with a visible marketplace label. Keep external orders out of dine-in table billing/session aggregation unless a separately approved workflow explicitly requires it.
- Treat marketplace payment collection and restaurant settlement as separate from customer-to-restaurant UPI verification and from the company's SaaS subscription gateway. Store provider-supplied payment/settlement facts; do not mark marketplace settlement as received without a verified settlement source.
- Menu/availability synchronization is a separate capability from order ingestion. It requires explicit item/modifier mapping, price/tax validation, publish acknowledgements and rollback/error visibility.
- Provide connection health, webhook lag, acknowledgement latency, failed status updates, retry queue depth and last successful event per tenant/location/provider.
- Do not scrape marketplace merchant portals, automate their UI, or ask restaurants to share marketplace passwords as an integration substitute.

12. GAMES, REWARDS AND CONTENT CONFIGURATION
--------------------------------------------

12.1 Games service boundary
~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Game catalogue and feature entitlement determine which games a tenant may expose.
- Game session belongs to tenant and optionally location/table session; session participant receives a short-lived room capability.
- Server validates session start/end, scoring rules, attempt limits and reward eligibility. Client-reported score is not authoritative.
- Use private room channels; never broadcast a tenant-wide event containing participant identity or private game state.
- Start with low-risk turn-based trivia/puzzles. Defer high-frequency real-time gameplay until load and abuse controls are understood.
- Do not expose customer phone/email on leaderboards; use pseudonyms or approved display names.

12.2 Reward safeguards
~~~~~~~~~~~~~~~~~~~~~~

[TABLE 31]
| Control | Technical requirement |
| --- | --- |
| Eligibility | Server checks game result, customer/session eligibility, tenant/location scope and configured conditions. |
| Limits | Per-user/day/session quotas, tenant reward inventory, expiry and branch applicability. |

12.3 No-code content configuration
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Owner-editable pages are rendered from a strict JSON schema of allowed content blocks. A block has a type, version and validated properties. The renderer maps each allowed type to a trusted frontend component. No arbitrary scripts, HTML execution or dynamic component imports are permitted.

[TABLE 32]

- Validate every block against a server-side allowlist/schema before save and publish.
- Separate draft from published version; publish is atomic and creates an audit record.
- Media references must point to tenant-owned storage assets; cross-tenant asset references are rejected.
- Cache invalidation follows publish; public pages render only the current published version.
- Provide preview in a sandboxed owner experience, not by executing user-provided code.

15.1 Mandatory acceptance scenarios
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Tenant A staff cannot read, mutate or subscribe to Tenant B data even when guessing IDs or changing URL/body parameters.
- A duplicate order submission using the same idempotency key does not create a second order/KOT.
- A customer-entered UPI reference does not mark a restaurant bill as verified paid.
- A valid staff member can verify restaurant payment and the audit record captures actor, amount, time and bill.
- A SaaS plan payment webhook activates the correct tenant subscription exactly once; invalid/duplicate events do not activate it again.
- A customer disconnecting during preparation can reopen the page and see the latest persisted status and ETA.
- A READY order reaches the correct waiter queue in table-service mode and the customer pickup notice in self-service mode.
- An expired or unentitled game feature cannot be started through a direct API request.
- Owner content with an unknown block type, invalid properties or cross-tenant asset ID is rejected.
- A failed integration job retries safely and does not duplicate attendance or stock records.
- A duplicate food-marketplace webhook cannot create a second external order or kitchen ticket.
- A webhook with an invalid signature, replayed timestamp or unknown outlet mapping is rejected/quarantined and cannot cross tenant boundaries.
- An authorized staff member can accept/reject a marketplace order from the staff dashboard; the connector records provider acknowledgement or a visible failure.
- A provider timeout during accept/reject triggers reconciliation before any potentially duplicate action is retried.
- A kitchen status update is mapped only to provider-supported statuses and does not overwrite a later cancellation/rejection event.
- External delivery orders do not require a dine-in table session and do not enter the dine-in consolidated bill by accident.
- Marketplace collection/settlement records are not confused with restaurant UPI verification or company SaaS subscription payments.
